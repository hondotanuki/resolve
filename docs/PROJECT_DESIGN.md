# 1. Overview

## 1.1 目的

- AtCoderとOnlineMathContest（OMC）の競技プログラミング・競技数学の問題をURLから登録する。
- 問題情報と学習履歴を確認し、目標時間を意識して取り組む。
- 学習結果に基づき、未着手の問題と復習対象をホームで確認する。

ユーザーは個人を想定し、ローカル利用を基本とする。開発者はC#、ASP.NET Core、Entity Framework Core、React、TypeScript、テスト、設計、Gitを学びながらアプリを完成させる。

## 1.2 この文書の見方

この文書の「新方針」は、これから実装するプロダクトの仕様であり、実装済みを意味しない。現在のAPI契約は「8.2 移行中の実装済みAPI契約」に区別して記載する。

現在のコードでは問題を `LearningItem` と呼ぶ。画面・仕様上は「問題」と呼ぶが、コード名・テーブル名を `Problem` に変更するかは未決定とする。

# 2. Scope

## 2.1 M2の新方針

- AtCoder・OMCの対応問題をURLから登録し、問題一覧・詳細で確認・編集する。
- 出典・コンテスト種別・問題区分から、バックエンドで定義した目標時間を適用する。
- 問題詳細で元の問題を参照し、タイマーを用いて取り組む。
- 正解・不正解と所要時間を学習記録として保存・訂正・削除し、履歴と現在状態を表示する。
- ホームに未着手とルールに基づく復習対象を別々に表示する。

## 2.2 後続で実装・検討するもの

- 固定の候補から問題にタグを手動で付ける機能。タグによる絞り込みはタグ付けの後に検討する。
- 問題のアーカイブ、検索・絞り込み・並び替えの具体的な範囲。
- URL取得方式の詳細、対応サイトの追加、各区分の目標時間の拡張。
- 公開方法や、個人利用を超える利用形態。

## 2.3 対象外

- 英語学習など、競技問題以外の学習対象。
- OpenAI・LLMによる復習推薦、難易度・タグの候補生成、プロンプト管理。
- 目標時間の画面からの変更。対応表の変更はコードで行う。
- MVPでのユーザー認証と複数ユーザー対応。

# 3. Use Cases

各UseCaseの入力は利用者の操作に必要な情報であり、DBの列をそのまま公開することを意味しない。IDや作成日時などシステムが決める値は、原則として利用者の入力に含めない。

## UC-I01 問題をURLから登録する

### 目的

元の問題URLから必要な情報を取得し、問題を管理対象に追加する。

### 入力

- 対応するAtCoderまたはOMCの問題URL。

### 処理

1. URLが登録済みの問題を指す場合は二重登録せず、既存の問題詳細を開く。言語指定だけが異なるURLは同じ問題として扱う。
2. 未登録の場合、出典に応じてタイトル・出典・コンテスト種別・問題区分を取得する。
3. 4項目が揃い、バックエンドの対応表に目標時間があることを確認する。
4. 問題を登録し、詳細を表示する。登録後に内容を修正できる。

### 結果

登録した問題、または同じ問題として既に登録された詳細を表示する。

### エラーケース

- URLが不正、対象外のサービス・問題、または対応表にない区分である。
- 問題情報の取得に失敗する、または必要な4項目のいずれかが取得できない。
- 登録に失敗する。取得失敗・未対応区分では部分的に登録しない。

登録済み問題の再入力や詳細表示では外部から再取得しない。外部からの手動更新は後続で検討する。

AtCoderはAtCoder Problemsの非公式データ、OMCは問題ページのHTMLを利用する方針とする。同じAtCoder問題でもコンテストが異なる場合は別に登録する。言語指定以外のURLパラメーターを無条件に削除しない。取得間隔・調査結果・未確認事項は [Issue #31の調査記録](issue31-problem-metadata-research.md) を参照し、同一性の具体的な表現は実装時に決める。

## UC-I02 問題一覧を確認する

### 目的

登録済みの問題全体を確認し、詳細へ移動する。

### 入力

- なし。検索・絞り込みは後続で範囲を決める。

### 処理

1. 通常表示の対象となる問題を取得する。
2. 問題の一覧を表示し、選択した問題の詳細を開く。

### 結果

登録済みの問題を確認できる。アーカイブ機能の導入後はアーカイブ済み問題を通常一覧から除外する。

### エラーケース

- 問題の取得に失敗する。

## UC-I03 問題詳細を確認する

### 目的

問題そのものの情報と学習履歴を確認し、取り組む。

### 入力

- 問題ID。

### 処理

1. 問題情報・元のURL・目標時間・現在状態を取得する。
2. 学習記録を取得し、詳細と履歴を表示する。
3. 元の問題を開く、タイマーを使う、情報または記録を編集する操作を提供する。

### 結果

問題情報と学習履歴が中心に表示され、必要なときに学習記録を追加できる。

### エラーケース

- 問題が存在しない、または情報・履歴の取得に失敗する。

## UC-I04 問題情報を編集する

### 目的

自動取得した問題情報の誤りを登録後に修正する。

### 入力

- 問題IDと修正する問題情報。

### 処理

1. 対象の問題を取得する。
2. 修正後の情報、URLの同一性、目標時間に対応する区分を検証する。
3. 問題を更新する。

### 結果

詳細・一覧に修正後の問題情報が表示される。

### エラーケース

- 問題が存在しない、入力情報が不正、別の登録済み問題と重複する、または未対応の区分である。

編集時に扱う具体的なフィールド・API表現は、URL取得調査と実装Issueで決定する。

## UC-I05 問題をアーカイブする（後続）

### 目的

不要になった問題を通常表示から除外し、履歴を保持する。

### 入力

- 問題IDとアーカイブ確認。

### 処理

1. 対象を取得し、利用者の確認後にアーカイブ状態にする。
2. 通常一覧・未着手・復習対象から除外する。

### 結果

学習履歴は保持される。

### エラーケース

- 問題が存在しない、または操作に失敗する。

## UC-R01 タイマーで学習記録を登録する

### 目的

問題に取り組んだ時間と正解・不正解を記録する。

### 入力

- 問題ID、タイマー操作、正解・不正解、メモ（任意）。

### 処理

1. 対応する問題区分の目標時間があることを確認し、タイマーを開始する。
2. 一時停止・再開を可能にし、一時停止中の時間を所要時間に含めない。
3. 目標時間に達したらアプリ内で通知し、計測を続ける。
4. 終了時に正解・不正解を選択し、所要時間と保存時に適用した目標時間を記録する。
5. 保存後、履歴・現在状態・復習判定を更新する。

### 結果

学習記録に正誤、所要時間、当時の目標時間と時間内・超過の判定が反映される。

### エラーケース

- 問題や対応する目標時間がない、入力が不正、または保存に失敗する。
- 計測中のアプリ内画面移動・再読み込み・タブ終了時は、計測結果を破棄する確認を行う。移動を取り消した場合は計測を継続し、破棄した場合は記録しない。再読み込み・タブ終了の確認表示や文言はブラウザの制約を受ける。

元の問題は別タブで参照することを想定する。目標時間の定義が計測中に変更された場合は、保存時に有効な目標時間を記録する。保存済みの記録は、その後の定義変更で再判定しない。

## UC-R02 学習履歴を確認する

### 目的

問題に対する過去の学習記録を確認する。

### 入力

- 問題ID。

### 処理

1. 対象に紐づく学習記録を学習日時の降順、同日時ではIDの降順で取得する。
2. 正誤・所要時間・記録時の目標時間・時間内／超過・メモを表示する。

### 結果

学習履歴を確認でき、記録がない場合は空状態を表示する。

### エラーケース

- 問題が存在しない、または履歴の取得に失敗する。

## UC-R03 学習記録を訂正する

### 目的

入力ミスのある学習記録を修正する。

### 入力

- 学習記録IDと修正内容。正解・不正解と所要時間を訂正できる。

### 処理

1. 対象の記録を取得し、修正内容を検証する。
2. 記録時の目標時間を維持し、修正後の所要時間に基づいて時間内・超過を判定する。
3. 現在状態と復習推薦を履歴から再計算する。

### 結果

修正後の履歴・現在状態・復習対象が表示される。

### エラーケース

- 対象が存在しない、入力値が不正、または更新に失敗する。

## UC-R04 学習記録を削除する

### 目的

誤って登録した学習記録を削除する。

### 入力

- 学習記録IDと削除確認。

### 処理

1. 指定された記録を取得し、利用者の確認後に削除する。
2. 残る履歴から現在状態と復習推薦を再計算する。

### 結果

削除した記録が履歴から消え、状態・復習対象に反映される。

### エラーケース

- 記録が存在しない、または削除に失敗する。

## UC-I06 問題にタグを付ける（後続で実装）

### 目的

問題を解法や考え方で整理する。

### 入力

- 問題IDと、アプリが用意した候補から選んだタグ。

### 処理

1. 問題詳細でタグを確認し、候補から追加・削除する。
2. 選択したタグが有効な候補に含まれることを確認し、問題との関連を保存する。

### 結果

1つの問題に複数のタグを付けられ、問題詳細で確認できる。タグは任意であり、URL登録時に入力する必要はない。

### エラーケース

- 問題が存在しない、候補外のタグが指定された、または保存に失敗する。

## UC-S01 問題を検索・絞り込みする（後続で検討）

### 目的

登録済みの問題を探しやすくする。

### 入力

- 検索条件。対象とする項目は後続で決める。
- タグによる絞り込みも候補とする。

### 処理

- 検索条件を検証し、一致する問題を取得・表示する。

### 結果

条件に一致する問題を一覧で確認できる。

### エラーケース

- 検索条件が不正、または取得に失敗する。

## UC-S02 ホームで未着手と復習対象を確認する

### 目的

次に取り組む問題を確認する。

### 入力

- なし。

### 処理

1. アーカイブされていない問題と学習履歴を取得する。
2. 記録のない問題を未着手、記録のある問題を復習ルールに基づき判定する。
3. 未着手と復習対象を別枠で表示し、それぞれの詳細を開けるようにする。

### 結果

アプリを開いた最初の画面で、未着手と復習対象を確認できる。

### エラーケース

- 問題または学習履歴の取得に失敗する。

# 4. Domain Model

Domain ModelはDBテーブルの写しではなく、問題・記録と、その制約や判断を表す。名称・クラス分割は実装時に再検討する。

| 概念 | 責務 |
| --- | --- |
| 問題（現行コードでは `LearningItem`） | タイトル、URL、出典、コンテスト種別、問題区分、アーカイブ状態を扱う |
| 問題区分と目標時間 | 出典・コンテスト種別・問題区分から、コード内の目標時間を決める |
| タグ（後続） | 二分探索などの固定候補と、問題に手動で付けたタグを扱う |
| `StudyRecord` | 1回の正誤、学習日時、所要時間、保存時の目標時間、メモを表す |
| `ItemStatus` | 未着手・要復習・完了を履歴から算出する |
| 復習判定 | 正誤・時間超過・連続成功・経過時間から復習対象を決める |

問題・記録の属性をどのEntityやテーブルに配置するか、タイマーの実装場所、URL取得結果の型は、取得調査と各実装Issueで決める。現在の `LearningItem`・`StudyRecord` は新方針の全属性をまだ持っていない。

# 5. Business Rules

## BR-01 アーカイブ

アーカイブ済みの問題は通常一覧・未着手・復習対象から除外し、学習履歴は保持する。アーカイブ操作自体は後続で実装する。

## BR-02 現在状態

現在状態はDBに保持せず、最新の学習記録から算出する。最新は学習日時の降順、同日時ではIDの降順で決定する。

| 最新の記録 | 現在状態 |
| --- | --- |
| 記録なし | 未着手 |
| 不正解 | 要復習 |
| 正解・時間超過 | 要復習 |
| 正解・時間内 | 完了 |

## BR-03 復習推薦

未着手は復習対象に含めず、ホームの別枠に表示する。アーカイブ済みは対象外とする。

| 最新の記録と連続成功 | 復習対象になる時点 |
| --- | --- |
| 不正解または正解・時間超過 | すぐ |
| 時間内正解が1〜2回連続 | 最新の学習日時から168時間後 |
| 時間内正解が3回以上連続 | 最新の学習日時から1440時間後 |

「連続成功」は時間内の正解を数え、不正解・時間超過で途切れる。しきい値にちょうど到達した時点から復習対象とする。復習対象かどうかは現在状態とは別に算出するため、状態が完了でも経過時間により復習対象になる。

## BR-04 問題区分と目標時間

出典・コンテスト種別・問題区分ごとの目標時間はバックエンドのコード内に分単位で定義し、画面から変更しない。ARCとARC++は目標時間の設定では同じRegular区分とするが、元のコンテスト名は表示できるようにする。

| 系列 | A | B | C | D | E | F | G |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| AtCoder Beginner（ABC） | 10 | 10 | 20 | 20 | 20 | 20 | 40 |
| AtCoder Regular（ARC・ARC++） | 30 | 40 | 50 | 100 | 100 | 100 | 100 |
| OMC Beginner（OMCB） | 5 | 10 | 10 | 10 | 15 | 15 | 20 |
| OMC Regular（OMC） | 10 | 10 | 20 | 20 | 20 | 20 | 40 |
| OMC Expert（OMCE） | 30 | 40 | 50 | 100 | 100 | 100 | 100 |

AtCoder Grand（AGC）は全問題120分。その他の系列で表にない区分は未対応とし、問題登録時にエラーとする。対象の実在・区分の判定はURL取得結果に基づく。

タイマーは目標時間に達した時点で通知する。所要時間が目標時間を超えた場合に時間超過とし、ちょうど同じ時間は時間内とする。記録時に適用した目標時間を保存し、後からコード内の定義が変更されても過去の判定を変えない。

# 6. Data Model

新方針で必要な情報を示す。具体的なテーブル分割・新規列名・型・MigrationはURL取得調査と各Issueで決定する。

| 対象 | 必要な情報 |
| --- | --- |
| 問題 | ID、タイトル、元URL、出典、コンテスト種別・表示名、問題区分、アーカイブ状態、作成・更新日時 |
| 学習記録 | ID、問題ID、学習日時、正誤、所要時間、保存時の目標時間、任意のメモ、作成・更新日時 |
| 目標時間の対応 | 出典・コンテスト種別・問題区分と時間。バックエンドのコード内で管理する |
| タグ（後続） | 固定のタグ候補と、問題とタグの関連。候補の管理方法とテーブル構成は実装時に決める |

1つの問題に複数の学習記録を関連付ける。現在状態や復習対象は記録から算出する。AtCoderではコンテストの文脈を同一性に含める。具体的な一意性の表現とURL取得元の識別情報の保持方法は、[Issue #31の調査記録](issue31-problem-metadata-research.md)を踏まえて実装時に決める。

現在のSQLite DBは検証用であり、実装時には作り直してよい。移行方法と開発データの扱いは実装Issueで明示する。この設計書の更新時点ではDBを変更しない。

# 7. Screen Design

各機能の実装時に、その画面のUI・操作性・エラー表示・テストまで仕上げる。具体的な配色、余白、文言は各Issueの着手時に決定する。

| 画面 | 目的と主な表示・操作 |
| --- | --- |
| ホーム | 最初に表示する画面。未着手と復習対象を別枠で確認し、問題詳細を開く |
| 問題一覧 | 登録済みの問題全体を確認し、詳細へ移動する |
| URL登録 | URLを入力し、自動取得・登録する。重複時は既存詳細、取得失敗時はエラーを表示する |
| 問題詳細 | 問題情報・元のURL・目標時間・現在状態・学習履歴を中心に表示し、編集やタイマーへ進む。後続でタグの表示・追加・削除を行う |
| タイマー・記録 | 開始・一時停止・再開、目標時間通知、正誤の選択、保存、画面移動時の確認を提供する |
| 問題・記録の編集 | 登録後の問題情報や学習記録を訂正し、結果を詳細に反映する |

各画面で必要な読み込み中・空状態・エラー状態を表示する。問題の登録フォームを常時中心に置かず、問題情報と学習履歴の確認を優先する。

# 8. API Design

## 8.1 新方針のAPI

必要な機能は、URLによる登録・問題一覧／詳細／編集、学習記録の登録／履歴／訂正／削除、未着手と復習対象の取得。新しいAPIのパス・Request／Response・エラー表現は、URL取得調査と各Issueで決める。

StudyRecord登録時のLocationに対応する `GET /study-records/{id}` は、復習推薦Issue内で追加する。現在のLocationは `/study-records/{id}` だが、単体GETはまだ存在しない。

日時はUTCを基準に扱う。学習日時はUTC入力・UTC出力とし、Frontendは利用者のローカル時刻で表示する。復習の168時間・1440時間は経過時間として判定する。

## 8.2 移行中の実装済みAPI契約

以下は**現在のコードの説明**であり、新方針への移行後の最終契約ではない。Issue #29時点の契約は [api-contract-inventory.md](api-contract-inventory.md)、現在の詳細はDevelopment環境のOpenAPI・Scalarを参照する。

- `GET /learning-items`、`POST /learning-items`、`GET /learning-items/{id}` がある。
- `GET /learning-items/{id}/study-records`、`POST /learning-items/{id}/study-records`、`PATCH /study-records/{id}`、`DELETE /study-records/{id}` がある。
- 問題は出典・コンテスト種別・問題区分で扱い、`itemType` は持たない。学習結果の `result` は `success`・`failure` のみ。
- `POST /learning-items` は `url` を受け取り、AtCoder・OMCから問題情報を取得する。必要情報や対応する目標時間がない場合は登録しない。URL・コンテスト識別子・コンテスト名・開始日は必須。
- 問題登録時は、対象外URLを400、目標時間のない区分を422、外部情報の取得失敗を502、外部取得のタイムアウトを504で返す。エラー詳細には利用者向けの `ProblemDetails` を使用する。
- 学習日時入力は `Z` 付きUTCを受け付け、`+00:00` を含むオフセット付き・タイムゾーンなしの入力を拒否する。所要時間は必須の0以上の32ビット整数で、数値文字列・小数・nullを受け付けない。記録は保存時の `targetSeconds` を持つ。
- 現在のレスポンスの `archivedAt`・`memo` は、該当する項目のあるレスポンスでは省略せずnullを返せる。問題の `content` は廃止した。
- 現在のPATCHは `result`・`studiedAt`・`durationSeconds`・`memo` の1項目以上を要求し、`memo` は明示的なnullで消去できる。Orval生成型に1項目以上の条件は反映されず、Frontend側のラッパーで補う。
- JSONの項目名は大文字・小文字を区別し、OpenAPIに記載されたcamelCaseを使う。未知の項目は無視し、未知の項目だけのPATCHは400を返す。

Frontendはまだ旧APIの手入力画面を使用しており、問題登録APIとの接続は後続で更新する。タイマーは未実装。

# 12. Testing Strategy

## Domain / Application

- 目標時間の対応・未対応、時間内・超過の境界、記録時の目標時間に基づく再判定。
- 最新記録と同日時のID順、未着手・不正解・時間超過・時間内正解の現在状態。
- 連続成功の1・2・3回、不正解・時間超過による中断、168時間・1440時間の直前と到達時。
- 履歴の訂正・削除による状態・復習対象の再計算。時刻はテストで固定する。

## Infrastructure / API

- サービス別の問題情報取得は外部サイトに依存しないテストデータで成功・失敗・未対応を確認する。実サイトでの取得可能性はSpikeで別途確認する。
- URL重複・言語指定、必要情報不足時の未登録、問題の取得・編集と学習記録の保存・訂正・削除を確認する。
- StudyRecord登録後のLocationから単体GETでき、存在しないIDに404を返すことを確認する。
- OpenAPIとFrontend生成型を実装後の契約に合わせる。

## Frontend / 手動確認

- URL登録の成功・重複・取得失敗、各画面の読み込み・空・エラー状態。
- タイマーの開始・一時停止・再開・通知・計測継続・破棄確認と記録保存。
- 記録訂正後の時間判定、ホームの未着手・復習対象と詳細画面への遷移。
- 各Issueでブラウザ操作、UI・操作性、キーボード操作、既存機能への影響を確認する。

# 13. Error Handling

- 不正なURL、対象外サービス、取得できない必須情報、未対応区分は利用者が原因を理解できるように表示し、問題を登録しない。
- 既存の問題を指すURLはエラーにせず、既存詳細を開く。
- 外部サイトやDBへのアクセス失敗は、取得・保存に失敗したことを画面に示す。具体的なHTTPステータスやエラー形式は各Issueで決定する。
- 存在しない問題・学習記録は404とする既存方針を維持する。

# 14. Decision Log

## D-001 SQLiteとEntity Framework Core

個人利用のMVPとC#・EF Coreの学習に合わせ、SQLiteとEntity Framework Coreを使用する。

## D-002 対象と名称

AtCoder・OMCの競技プログラミング・競技数学の問題を扱う。画面では「問題」と呼び、現行の `LearningItem` のコード名・テーブル名の変更は未決定とする。

## D-003 URLによる登録

URLから必要な4項目を自動取得して登録し、同じ問題の再登録時は外部への再アクセスをせず既存詳細を開く。AtCoderはAtCoder Problemsの非公式データ、OMCは問題ページのHTMLを使う。AtCoderの同一問題でも異なるコンテストなら別登録とする。詳細と未確認事項は [Issue #31の調査記録](issue31-problem-metadata-research.md) を参照する。

## D-004 目標時間と学習記録

目標時間は問題区分ごとにコード内で管理し、記録には保存時の目標時間を残す。正誤と時間内・超過を別々に扱う。

## D-005 復習推薦

正誤、時間超過、連続成功、経過時間による決定的なルールで復習対象を選ぶ。

## D-006 UIの進め方

各機能の実装時に、その画面の表示・操作性・エラー・テストを仕上げる。ホームを最初の画面とし、未着手と復習対象を別枠で表示する。
